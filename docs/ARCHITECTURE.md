# Project Velocity: technical architecture

Working title **VELOCITY: Anti-Gravity League**. This is an original anti-gravity racing game for
Android. It belongs to the genre of the late-90s anti-gravity racers but uses none of their names,
ships, tracks, music, logos or art.

## 2. Engine decision: Godot 4.7 instead of Unity 6

Unity requires an interactive Unity ID sign-in and licence activation that cannot be done from this
environment. Without the editor UI, writing scenes and prefabs by hand is also fragile. Godot 4.7
was already set up end to end for Android on this machine. The owner chose Godot when asked.

How each Unity requirement in the brief maps onto Godot:

| Brief (Unity) | Godot 4.7 equivalent used here |
|---------------|--------------------------------|
| URP | Mobile renderer (Vulkan), with GLES3 Compatibility as fallback |
| C# | GDScript (typed). It is portable to Android without Mono, and all systems can be tested headless |
| Input System | `Input` + per-finger touch tracking (`TouchControls`), gamepad via `Input` joypad API |
| Addressables | Scripts and resources are loaded on demand with `load()`. The track world is built at load time from compact data, so there is nothing large to stream |
| Audio Mixer | `AudioServer` buses (Master → Music / SFX / Engine / UI) with effects |
| Custom shaders | Godot shading language (`assets/shaders/*.gdshader`) |
| Inspector-exposed tuning | `ShipSpec` holds all handling parameters as one plain data object, editable in code or through `tools/handling_bench.gd` and the in-game telemetry overlay |

## 3. Core principles

1. **Handling first.** The ship simulation is custom, deterministic, pure data (no nodes, no
   Godot physics bodies) and covered by headless tests. Visuals read from it and never feed back
   into it.
2. **The track is a data structure, not a mesh.** Physics, AI, the camera, progress and respawn all
   query an analytic track frame table (`TrackData`). The render mesh is generated from the same
   data, so the visible surface and the physical surface always agree. Ships cannot tunnel through
   walls or the floor at any speed, because contact is a comparison of lateral offset and height,
   not a raycast against triangles.
3. **Everything is generated by code.** Meshes come from `MeshKit`, textures from
   `tools/gen_textures.py`, audio and music from `tools/gen_audio.py`. Nothing is downloaded except
   the two OFL fonts.
4. **Every claim is backed by a test or a measurement.** There are unit tests for the physics and
   the track, automated race runs with AI drivers and screenshots, and a telemetry printout.

## 4. World scale and speed

- 1 unit = 1 m. Ship ≈ 5.6 m long and 2.6 m wide. Track 22–34 m wide.
- The speed readout uses the **league speed scale ×2.0**: displayed km/h = m/s × 3.6 × 2.0.
  This is a deliberate fiction. At true 1:1 scale the brief's 500–900 km/h would be 140–250 m/s,
  which no-one can react to on a phone screen. The ×2 scale keeps the readout in the brief's range
  while the motion stays readable.

| Class | Sim top speed | Displayed | Use |
|-------|---------------|-----------|-----|
| SPARK | 72 m/s | ~520 km/h | Entry |
| ARC | 90 m/s | ~650 km/h | Default race class |
| NOVA | 110 m/s | ~790 km/h | Expert |
| QUASAR | 130 m/s | ~940 km/h | Unlockable |

## 6. Track representation

A circuit is authored as a sequence of segments in `TrackSpec`: length, yaw turn, pitch change,
target bank, target width, and tags (tunnel, gap/jump, boost pad, weapon pad, pit/recharge, split).
`TrackBuilder` integrates the segments into a dense centre line every 1 m:

- Yaw and pitch curvature use **smooth ramp-in/ramp-out profiles** (no curvature steps), so every
  corner has natural transitions.
- Bank and width are interpolated with smoothstep between segment targets.
- **Closure**: the leftover heading error is spread over the turns, and the leftover position error
  is spread linearly along the lap. The builder reports the residual.
- Frames: `T` = tangent; `N` = zero-roll up rotated by bank about `T`; `B` = `T × N` (right).

`TrackData` stores the samples (`pos`, `T`, `N`, `B`, half-widths, bank, `s`) and answers:

- `project(world_pos, hint) → s, d (lateral), h (height above surface), frame`. This is a local
  search from the previous sample, so it is O(1) per query and correct where the track crosses
  over itself.
- `surface_at(s, d)`, `frame_at(s)` (interpolated), `curvature_at(s)`, plus tags by s-range.

## 7. Ship physics (`ShipPhysics`)

World-space simulation at **120 Hz** (60 Hz physics tick × 2 substeps), with interpolated rendering
for 90/120 Hz displays.

- **Surface probes**: four probes at the hull corners are projected onto the analytic surface.
  A plane fit through them gives the ship's target up vector and its height. Crests and valleys
  therefore pitch the hull naturally.
- **Hover**: a spring-damper holds the hover height along the surface normal. Inside the lock range
  ("flux lock") gravity points along −N (track gravity), so banked walls and steep sections hold the
  ship, and a saturated pull-down keeps it on crests. Above the hold limit (v²κ > g_track + pull_max)
  the ship leaves the surface. A hard floor clamps any compression below the minimum clearance:
  the hull never enters the track, and it scrapes with sparks and speed loss instead.
- **Orientation**: the up vector follows the probe plane through a critically damped angular spring.
  Yaw is its own inertial state.
- **Planar handling**: the heading turns at the yaw rate. Velocity is redirected towards the
  heading, limited by the hull's lateral force capacity `a_lat`. Asking for more yaw than the grip
  supports builds slip angle (drift), and slip costs speed (scrub).
- **Steering**: target yaw rate = progressive input × min(ω_low, k·a_lat / v), approached with yaw
  inertia.
- **Airbrakes (independent L/R)**: each adds drag proportional to speed, a yaw moment towards its
  side, and extra lateral capacity on that side. A light touch tightens the line. Both together
  brake and stabilise.
- **Thrust**: a = thrust·A0 − A0·(v/v_top)²·(0.35 + 0.65·thrust). Top speed is v_top, and coasting
  at speed decelerates at ≈0.35·A0.
- **Slopes**: the planar component of world gravity accelerates downhill and slows uphill, and on
  steep banks it pulls inwards. It fades out on decks rolled past ~55°.
- **Rolling decks**: a co-rotating lock turns the velocity and orientation with the deck's roll, so
  corkscrews drive like straights (see `docs/HANDLING.md`).
- **Walls**: analytic barriers at the track edge. The response is restitution, friction speed loss
  proportional to impact speed, a yaw kick away from the wall, energy damage, and sparks. Glancing
  contact slides instead of sticking.
- **Ship–ship**: two circles per hull, with penetration resolution and impulse exchange.
- **Airborne**: world gravity ×1.5, and the nose eases towards the flight path. On landing, the
  inbound normal speed is absorbed by the cushion and very hard impacts scrub speed.

All tuning lives in `ShipSpec` (team stat ratings → physical parameters per speed class).

## 8. Cameras

`CameraRig` smooths the **orientation** frame it follows (yaw/up), not the world position. At
100 m/s a position spring would trail the ship by metres, so the camera stays tight while still
reading drift and banking. Speed controls FOV (68° → 92°), pull-back and look-ahead along the
track. The rig also rolls with the bank, rises over crests, and clamps inside the barriers and
tunnel ceilings. Modes: standard, wide, close, cockpit, and a replay/trackside camera for the finish.

## 9. AI

At load time, `RacingLine` computes a minimum-curvature line by iterative elastic smoothing in track
space, plus a speed profile: lateral limit, then a backward braking pass, then a forward
acceleration pass. `AIDriver` produces the same `ShipControls` that a player does: steering from a
look-ahead pursuit of the line, airbrakes when the yaw demand exceeds steering or the speed exceeds
the profile, and thrust. An edge guard predicts the hull's lateral position 0.45 s ahead and steers
off a barrier before contact. Pure pursuit toward a line that hugs the edge can otherwise overshoot
it at steep crossing angles. A slip guard eases the steering and keeps the inside airbrake out once
the nose points more than 6° inside the direction of travel. Beyond that point, extra yaw only
feeds a slide, because the keels can turn the velocity at a_lat / v at most. Each personality sets line bias, braking margin, overtaking and blocking
behaviour, consistency, and weapon use. Difficulty scales the profile margin and the reaction noise.
There is **no rubber-banding** and no hidden speed boosts.

## 10. Rendering budget (target: Galaxy A56-class GPUs at 60 fps)

- Mobile renderer. One directional light with shadows only on the ships at High and above.
  Baked vertex-colour occlusion. Emissive materials plus glow (bloom).
- Track: generated mesh in chunks of about 100 m, each with its own culling AABB, using shared
  materials.
- City: MultiMesh instancing for tower and window modules, a shader-driven window/emissive grid,
  and visibility ranges as LOD.
- Speed effects: FOV, speed streak particles, an optional motion-blur/chromatic post pass
  (full-screen quad, quality-gated), engine trails, and trackside light rhythm.
- Quality presets Low/Medium/High/Ultra, plus adaptive resolution to hold the frame-rate cap.

## 11. Risks and constraints

| Risk | Mitigation |
|------|------------|
| No phone connected: performance can't be verified | Budgets per preset, a desktop profiling proxy, and telemetry built in. On-device measurement is listed as an open item, not claimed. |
| GDScript CPU cost of 8 ships at 120 Hz | O(1) local projection queries, pure-data physics, AI at reduced update rates, and a measurement in the handling bench |
| Scope of the brief (12 tracks, 8 teams, all modes) | Staged delivery exactly as the brief demands. Milestone 1 (one ship, one circuit, AI, full race) comes before content expansion. Unbuilt items are listed, never hidden. |
| Touch steering precision | Analogue tilt plus touch-slider steering, a wind-on ramp for digital buttons, airbrakes under the thumbs, optional auto-thrust |
| Procedural art looking generic | Art direction document; hand-authored silhouettes in code (lofted hull sections, not boxes); layered scenery with landmarks |
